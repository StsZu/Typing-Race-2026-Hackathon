## 1. Мета

Навести лад у папках, документації та словникових матеріалах, після чого підготувати статичний HTML-сайт для запуску хакатону через GitHub Pages.

Публічний репозиторій має виконувати три функції:

1. пояснювати ідею та правила хакатону;
2. надавати учасникам технічне завдання й дозволені словники для завантаження;
3. бути безпечним для публікації: без секретів, службових файлів і матеріалів із неперевіреними правами.

## 2. Поточний стан

## 3. Критичне правило перед початком

**Не виконувати `git init`, staging, commit або публікацію, доки матеріали з неперевіреними правами не відокремлені від публічної частини.**

`.gitignore`, доданий після першого коміту, не прибере файли з історії Git. Тому правове розділення має бути завершене до створення репозиторію.

## 5. Обмеження безпеки

1. Не видаляти файли. Непотрібне для публікації переносити до локального архіву після підтвердження власника.
2. Перед кожним переміщенням зафіксувати старий і новий шлях у таблиці міграції.
3. Не змінювати вміст словників, вправ і радіодиктантів під час упорядкування.
4. Після копіювання або переміщення звіряти SHA-256.
5. Не публікувати TT або радіодиктанти без підтверджених прав.
6. Не додавати `.env`, токени, паролі, приватні ключі або персональні дані.
7. Не приписувати всьому репозиторію одну ліцензію, яка суперечить ліцензіям окремих наборів.
8. Не робити commit або deploy автоматично.

## 7. План виконання

### Етап 1. Повна інвентаризація

1. Побудувати список усіх файлів без читання `.git`, якщо він з'явиться.
2. Для кожного набору визначити:
   - мову;
   - тип: словник, частотний список, Hunspell, курс, вправа, текст, документація;
   - джерело;
   - ліцензію;
   - дозвіл на публікацію;
   - кількість файлів і записів;
   - розмір;
   - SHA-256.
3. Знайти точні дублікати за SHA-256.
4. Окремо позначити:
   - дублікати зібраних Tutor JSON і сирих TT-вправ;
   - згенеровані файли;
   - службові `.DS_Store`;
   - файли без визначеного джерела;
   - файли з невизначеним правом на поширення.
5. Зберегти звіт інвентаризації у `docs/DATA_INVENTORY.md`.

Критерій завершення: кожен файл належить до одного відомого набору або явно позначений як невідомий.

### Етап 2. Правове розділення

1. Сформувати три статуси:
   - `PUBLIC` — можна публікувати з наявною ліцензією;
   - `REVIEW_REQUIRED` — право не підтверджено;
   - `EXCLUDED` — службове або нерелевантне.
2. До `PUBLIC` включати лише набори з ліцензією та збереженим текстом ліцензії.
3. TT та радіодиктанти залишити `REVIEW_REQUIRED`.
4. Підготувати `docs/DATA_POLICY.md` із правилами додавання нових словників.
5. Показати власнику перелік майбутніх переміщень до `_private/` і отримати підтвердження.
6. Лише після підтвердження виконати переміщення без зміни вмісту.

Критерій завершення: жоден файл `REVIEW_REQUIRED` не входить до майбутнього Git-індексу й не має посилання для завантаження на сайті.

### Етап 3. Упорядкування папок

1. Перенести відкриті словники в `dictionaries/<language>/wordlists/`.
2. Перенести авторські навчальні банки в `dictionaries/<language>/training/`.
3. Не об'єднувати файли різних джерел в один список.
4. Зберегти оригінальні назви файлів усередині наборів.
5. Документацію із кореня перенести до `docs/`, крім головного `README.md`.
6. Порожню або застарілу структуру не видаляти без дозволу; спочатку показати список.
7. Створити таблицю `старий шлях → новий шлях` у `docs/DATA_INVENTORY.md`.
8. Після переміщення перевірити, що всі файли побітово збігаються з попередніми копіями.

Критерій завершення: із назви шляху зрозумілі мова, тип матеріалу, джерело та публічний статус.

### Етап 4. Маніфест і контрольні суми

1. Оновити `dictionaries/manifest.yml`.
2. Для кожного публічного набору вказати:
   - стабільний `id`;
   - мову;
   - тип;
   - джерело й URL;
   - ревізію або дату знімка;
   - ліцензію;
   - шлях до ліцензії;
   - файли, формати, кількість записів і розмір;
   - рекомендований спосіб використання.
3. Не включати абсолютні локальні шляхи до публічного маніфесту.
4. Перегенерувати `CHECKSUMS.sha256` лише для публічних матеріалів.
5. Додати `scripts/verify-data.sh`, який перевіряє суми та завершується ненульовим кодом при розбіжності.
6. Перевірити JSON, YAML, UTF-8 і заявлену кількість Hunspell-записів.

Критерій завершення: чистий клон може перевірити всі публічні дані однією командою.

### Етап 5. Головна документація

Оновити `README.md`, щоб він містив:

- короткий опис хакатону;
- для кого він;
- суперприз 10 000 грн;
- посилання на технічне завдання;
- перелік доступних українських та англійських словників;
- швидкий старт для учасника;
- спосіб перевірки контрольних сум;
- правила ліцензування й атрибуції;
- спосіб поставити запитання;
- поля дедлайну, журі та форми подання, які має заповнити організатор.

Створити `docs/PARTICIPATION.md` із правилами подання роботи:

- URL репозиторію учасника;
- URL демо;
- короткий опис навчальної моделі;
- декларація використання AI;
- перелік використаних словників;
- результати тестів;
- контакт учасника або команди.

### Етап 6. Статичний HTML-сайт

Створити сайт без обов'язкового backend і без build-кроку. Базова версія повинна працювати після відкриття через локальний статичний сервер і на GitHub Pages.

#### Обов'язкові секції `index.html`

1. **Hero:** назва хакатону, короткий заклик, приз 10 000 грн, кнопки «Прочитати ТЗ» і «Завантажити словники».
2. **Ідея:** сенсорний набір, одна клавіша — один палець, руки повертаються в базове положення.
3. **Три етапи навчання:** клавіатурні гами, слова з відкритих клавіш, частотні комбінації та швидкість.
4. **Завдання учасника:** стислий перелік обов'язкового функціоналу.
5. **Каталог даних:** картки дозволених наборів за мовою.
6. **Картка набору:** назва, мова, формат, кількість записів, розмір, ліцензія, джерело, кнопка завантаження.
7. **Критерії оцінювання:** таблиця зі 100 балами з технічного завдання.
8. **Як взяти участь:** кроки від форку/клону до подання роботи.
9. **Строки та контакти:** заповнювані організатором поля.
10. **FAQ:** AI, дозволені технології, командна участь, використання власних словників, авторські права.
11. **Footer:** GitHub, технічне завдання, джерела, політика даних.

#### Вимоги до HTML

- семантичні `header`, `main`, `section`, `nav`, `footer`;
- одна основна мова сторінки — українська;
- коректна робота від 320 px до широкого екрана;
- клавіатурна навігація й видимий фокус;
- достатній контраст;
- жодного посилання на `_private/` або обмежені матеріали;
- локальні CSS та JavaScript без обов'язкових CDN;
- відсутність форм, які удають відправлення даних без backend;
- усі кнопки завантаження ведуть на реальні публічні файли;
- сайт працює без AI API та секретів.

Критерій завершення: сторінка повністю пояснює хакатон людині, яка вперше відкрила посилання.

Створити `.gitignore` щонайменше для:


Перед `git init`:

1. перевірити, що `_private/` і `.DS_Store` не потраплять у репозиторій;

3. не використовувати Git LFS без реальної потреби: поточні окремі файли менші за ліміт GitHub, але рішення зафіксувати в README;
4. узгодити ліцензію коду сайту й документації;
5. не накривати ліцензією репозиторію сторонні словники — для них діють власні ліцензії.

Після цього підготувати команди ініціалізації, але не виконувати commit і push без окремої вказівки власника.

## 8. Автоматичні перевірки

Мінімальний набір:

1. SHA-256 усіх публічних даних збігаються.
2. `manifest.yml` синтаксично коректний.
3. Усі JSON-файли парсяться.
4. Усі текстові файли читаються як задеклароване кодування.
5. Hunspell `index.dic` має стільки записів, скільки вказано в заголовку.
6. У маніфесті немає абсолютних локальних шляхів.
7. У публічній частині немає `.DS_Store`, `_private`, `.env`, ключів або токенів.
8. Усі внутрішні посилання Markdown існують.
9. Усі локальні посилання `index.html` існують.
10. HTML проходить базову перевірку структури й не має дубльованих `id`.
11. Сторінка відкривається локально без помилок у консолі.
12. Сайт не посилається на набори зі статусом `REVIEW_REQUIRED`.
